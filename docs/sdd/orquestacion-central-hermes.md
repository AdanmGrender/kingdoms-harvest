# SDD harness orchestration (central = leader)

## When to Use
The user hands Central a project goal, a feature, or "sigue con el trabajo" on a repo that uses (or should use) the SDD harness from https://github.com/santvallejos/SSD-HARNESS-TEMPLATE. Central is the operations director: it decomposes, dispatches through the Kanban board, and holds the human gate. It does not write application code itself.

## Roster (profiles created for this; lean toolsets, role rules in each SOUL.md)
| Profile | Model | Toolsets | Job |
|---|---|---|---|
| central | claude-opus-5-5 | full + kanban | leader: decompose, create tasks, human gate, unblock, report |
| spec-author | claude-sonnet-5-5 | file, terminal, skills, todo | specs/<name>/{requirements,design,tasks}.md, status spec_ready |
| implementer | claude-sonnet-5-5 | file, terminal, code_execution, web, skills, todo | executes tasks.md with inline Evidencia, commits on feature/<name>, requests review |
| reviewer | claude-haiku-5-5 | file, terminal, skills, todo | review.md; APPROVED closes (done + CHANGELOG); else request_changes |
| visual-reviewer | claude-sonnet-5-5 | file, terminal, skills, todo, vision, code_execution | visual_review.md: every visual claim in spec/tasks/review vs. what captures/video frames show; APPROVED or CHANGES_REQUESTED via kanban_complete; never edits code |
| explorer | claude-haiku-5-5 | file, terminal, web, skills, todo | read-only research to a file |
| p-kh | claude-opus-5-5 | full + kanban | kingdoms-harvest project agent: coordinates its project and is art director (signs off art via Kanban tasks assigned to it); dispatches work to the board, never runs it itself |

The harness template is cloned at `D:\Proyectos\_harness-template`.

## Adopting the harness in a repo
1. Check the repo is clean (`git status`); work on a branch `chore/sdd-harness`.
2. Copy `.claude/agents/`, `AGENTS.md`, `docs/specs.md`, `specs/README.md`; copy and rename the `*.template*` files (`CLAUDE.md`, `feature_list.json`, `CHANGELOG.md`, `docs/architecture.md`, `docs/conventions.md`). If the repo already has a CLAUDE.md/AGENTS.md, merge instead of overwriting and tell the user.
3. Fill `docs/architecture.md` and `docs/conventions.md` from the real code. This is a reading job: dispatch it to `explorer` (it writes drafts), then Central checks them. Fill `feature_list.json` from the user's goals, one feature per independently shippable unit, `sdd: true` unless trivial.
4. Commit and tell the user what was added.

## Dispatch pattern per feature (Kanban)
Every task body carries: repo path, feature `name`, branch `feature/<name>`, and the one-line expected output. Never paste spec or code into bodies; agents read from disk (anti-telephone rule).
1. (Complex only) 1-3 `explorer` tasks with narrow questions -> `specs/<name>/research-*.md`.
2. `spec-author` task (parents = explorers). workspace_kind=dir, workspace_path=<repo>.
3. `implementer` task with parents=[spec task] and `initial_status="blocked"`, title prefixed `[GATE]`. This is the human gate: it stays blocked until the user says "aprobado".

Launch recipe (one pass, so the gate later needs only the owner's word): create the worktree from the integration branch *after* the prerequisite merges, create its two node_modules junctions right away (see Worktree lifecycle), then create brief → spec → [GATE] in one script with `hermes kanban create "<title>" --body-file <file> --assignee <profile> --parent <prev id> --workspace "dir:<worktree>" --max-runtime <s> --created-by central --idempotency-key <project>-<feature>-<role> [--initial-status blocked] --json`. Write bodies to scratch files and use `--body-file` (multi-line bodies with backticks and quotes break in shell `--body`); the idempotency key makes a retried script return the existing id instead of duplicating the task. Gate bodies that still listed "junctions pending" as a second unblock condition stalled until Central could run mklink, so do it before dispatch. Confirm the chain with `hermes kanban list | grep <feature>` (expect ready / todo / blocked) and log the ids in ESTADO.md.

Features that need generated art (sprites, pose sheets, backgrounds): the explorer and spec bodies forbid generating art; the brief inventories what exists vs. what is missing and counts the generations needed; the spec's design.md must carry an art plan (what, how many generations, volume options S0/S1/S2) marked as an owner decision plus the p-kh gate points, and tasks.md must stage the work so each stage fits one implementer run, with a no-new-art stage first. KH art is generated only through the free web tooling (see `references/kh-art-pipeline.md` §Generate): the art stage body names the web script, forbids the API path and `server/.env`, caps total generations for the stage (net count + regenerations, e.g. 21 net → cap 40), asks for the count in the summary, and tells the worker to pass existing sheets as `--ref` because the web model differs from the set already in the repo. Volume is still the owner's call (time, daily limit), not a spend decision.
4. When the spec task completes, read the stage headings and the design's open-questions section. Show the owner a stage table, then only the questions that are theirs, each with a recommendation. Route art questions to the art owner as tasks later, and flag any paid generation (API key, cost) as needing an explicit OK. Then tell the user: `Spec listo en specs/<name>/. Revisalo y di 'aprobado'`. Do not summarize the spec in chat beyond 3 lines.
5. On "aprobado" (or "apruebo todo", which covers every gate, open question and merge offer listed in the last report): set the feature to `in_progress` in feature_list.json (surgical edit) and commit it with the owner's answers in the message (e.g. `spec aprobado (Q1 si, Q3 si, Q4 si)`). Then `kanban_comment` the implementer task with each answer and the stage order (A -> request_review -> B -> C). Then `kanban_unblock`. Art-agent decisions (e.g. a font pick, an icon list) are tasks that Central itself creates for the art agent and links as `parents` of the stage task that needs them. Tell implementers in the body to NOT create board tasks, because a Sonnet/Haiku worker has reported a gate task as created when it never existed, and the stage then waits on nothing.
6. The implementer calls `kanban_request_review(reviewer="reviewer")`; the reviewer completes (APPROVED) or calls `kanban_request_changes` (requeues the implementer). Central only reads the one-line summaries.
7. On APPROVED: spot-check the claim (`git log`, `diff --stat` against the base, the head of review.md), then report to the user and offer to merge/push `feature/<name>` (merges and pushes need the user's OK). After the OK, follow the worktree lifecycle below.

Staged features (A/B/C): run one implementer task per stage. When the reviewer APPROVES a stage, Central:
1. checks `git log` and the unchecked `- [ ] T` lines in tasks.md;
2. creates any art-decision task the next stage needs;
3. creates the next stage task with `parents=[art task]`. The body names the exact T-range, carries over the reviewer's non-blocking notes as must-dos, and says "if near the runtime cap: commit, mark progress in tasks.md, kanban_block(kind=transient)".

If the art agent answers a later question early (in its completion summary), copy the answer into a comment on the next stage task instead of opening another task. feature_list.json and CHANGELOG stay untouched until the last stage closes.

One implementer task can carry a whole feature with art gates instead of one task per stage:
- Each instruction comment names the T-range, the stop point and the exact exit: `kanban_block(kind="needs_input", reason="T10: <sheet> listo para p-kh; N llamadas; dudosos: …")`.
- On the block, Central views the evidence and creates the art task for p-kh.
- On the verdict, Central comments the next T-range plus p-kh's rules, then calls `kanban_unblock`.
- The board's loop guard allows 2 `needs_input` blocks per task (`block_loop_detected`, limit 2): the second gate block drops the task to `triage`, not `blocked`, and it cannot be resumed from there. After the verdict, create a continuation task on the same worktree: body = state at creation (what is committed, what is uncommitted, generations used) + the verdict and next T-range + "read `hermes kanban show <old id>` for history" + the original body's rules. Use its own idempotency key, comment the old task with the new id, then `hermes kanban archive <old id>`. A stage with 3 gates (P1-P3) always hits this, so plan one implementer task per ≤2 gates and batch lots into one gate where possible (see the round-2 exception).

Workers sometimes run past the stop point, for example by doing a paid step that was declared out of scope. If the result is inside the owner's approval and passes verification, accept it and comment a scope reminder. Otherwise revert it. Either way, tell the owner it was a decision Central took.

Every implementer body that may start a dev server (Vite, the node server) must say: stop it before completing. An orphan dev server keeps the port busy and locks the worktree, so `git worktree remove` fails, and Central may not be allowed to kill it.

Small fixes with `sdd: false` (a broken test, a typo-level bug) skip spec and gate: one implementer task, often pinned to Haiku, that ends in `kanban_request_review`. The body must forbid deleting/skipping the test or changing the expected value just to pass, unless it is justified with file:line evidence that the current behavior is intended.

Big briefs: when the explorer's brief shows a feature touching dozens of files (e.g. hundreds of emoji→icon swaps), propose to the user splitting it into stages before the spec, so each approval is small and each implementer run fits its runtime cap.

## Visual review (mandatory for anything the player sees)
The owner requires a reviewer that contrasts what is SEEN (captures, video frames, contact sheets) with what is WRITTEN (requirements, design, tasks `Evidencia:`, review.md, commit messages). Green tests and a code APPROVED do not prove the scene looks right: layout bugs (actors floating over the background's sky, enemy/hero scale mismatch, damage numbers over faces, semi-transparent corpses left on the field, crowded heroes aiming away from targets) pass code review because no one opens the running scene.
1. Order per visual stage: implementer → code `reviewer` reaches `APPROVED` → `visual-reviewer` → owner OK. A `review_requested` handoff is not code-review approval: verify the reviewer’s terminal Kanban outcome before creating or dispatching visual review. If the owner confirms or restates the sequence mid-run, record it as a Kanban comment on the active task so the worker and downstream reviewer see the gate. Treat a code reviewer that escalates "cannot see images" the same as an APPROVED: hand off to visual-reviewer instead of opening the images yourself in a long Opus turn.
2. Task body (`--assignee visual-reviewer --max-runtime 2700`, same worktree, idempotency key `<feature>-visual-r<N>`): branch + HEAD sha, the spec sections with visual claims (by R-number), existing captures/video folders, the recapture script with free ports (vite :5173 + server :3001 when no worker uses them) and the seed script, and every known suspicion as a numbered confirm/discard item with the file:line you suspect. Exclude what the owner decides (e.g. device fps).
3. Output: `specs/<name>/visual_review.md`, one section per round, each claim `[OK|FALLA|NO VERIFICABLE]` with capture + region, plus "unwritten findings" with severity and a one-line fix. CHANGES_REQUESTED → implementer fix task (e.g. `T<n>.6 fix visual`) with the blocking findings verbatim + "recapture the same views" → code review → visual round N+1. APPROVED → next stage, or owner merge OK citing both review files.
4. Wire it into the relay cron prompt (rule for `review`/reviewer done) so it runs without Central; update the prompt with `hermes cron edit <id> --prompt "$(cat <prompt file>)"`.
5. Whenever Central itself views a capture or video for any reason (art identity, a pilot), run the full layout checklist above, not only the question it was looking for — the owner notices layout bugs Central skipped while checking something narrower. Before telling the owner a stage "looks fine", Central opens the key captures itself.
6. Converge, do not chase. Open-ended visual rounds never end: each round finds new things and the owner reads it as "seguimos corriendo detrás de problemas". Before (or at the latest after round 2 still finds new defects), write a numeric visual sheet `specs/<name>/hoja_visual.md` with rules V1..Vn that each carry a measurable threshold (hero/enemy height ratio, feet within ±N px of the background's ground line, max overlap %, damage-number size and position relative to the head, no `…` truncation at the listed resolutions, death = fall + lying at alpha ≥0.8, attacker faces target, result banner ≤40 % height, HUD labels match the sprites shown) plus the mandatory views (resolutions × enemy counts + result screens). Have the implementer apply ALL of it in one round, write a script that measures what it can into `hoja_medidas.json`, and put a V1–Vn table in the commit. Declare it the last visual round: visual-reviewer judges ONLY against the sheet, new non-sheet findings go to a later backlog. Performance (fps p5 on device) is always its own task, never part of the visual round. Ask the owner only the 1–2 taste decisions the sheet needs (e.g. which side to rescale), each with a recommendation and a "si no contestás sigo con la recomendada" default.
7. Motion/animation evidence for the owner: phone-size full-scene recordings make code-driven motion (breathing, weight shift, anticipation, recoil) invisible, so the owner says they "don't see" it. Record at 2× viewport, crop per group (heroes / enemies) and slow it down; recipe in `references/mobile-visual-qa.md` §4. Code motion must also read at real phone size: spec amplitudes that are clearly visible at 412 CSS px wide, and expose one intensity multiplier so it can be tuned with the owner watching. For multi-actor combat, assign deterministic, non-overlapping reserved slots (use staggered rows when a single row cannot fit); animate each actor through its own container/corridor and never reflow or tween teammates as a side effect. Test companions' coordinates during idle, attack, hit, and KO; they must change only from their own animation.

Profile setup (once per machine): `hermes profile create visual-reviewer --clone-from reviewer --description "..."` (cloning keeps the force-loaded `sdlc-review` skill), `hermes -p visual-reviewer config set model.default claude-sonnet-5-5` (Haiku cannot judge images), add `vision` and `code_execution` to its `platform_toolsets` in config.yaml, confirm with `hermes -p visual-reviewer tools list`, and replace the cloned SOUL with the claims-vs-image protocol (template: `templates/visual-reviewer-SOUL.md`). Add a roster row.

## Worktree lifecycle
- Base a new feature branch on the most integrated branch that contains its inputs (e.g. the art director's brief), not on an older feature branch. If the branch has no commits of its own and the task has not started, recreate it (`reset --hard <base>`) instead of merging.
- Dry-run cross-feature merges before dispatch: `git merge --no-commit --no-ff <other>`, list `--diff-filter=U`, then `merge --abort`. Tell the spec task the exact merge to do in a comment.
- Merge an approved feature: in the integration checkout, check `git status` (do not touch the owner's untracked files), `merge --ff-only feature/<name>` when the base is an ancestor, push, and verify with `git ls-remote origin <branch>` (a single-ref `fetch` can fail with "Needed a single revision" even when the push worked). If it is not an ancestor, use `merge --no-ff`. For the known `.gitignore` append conflict, delete only the three marker lines, `grep -c -E "^(<<<<<<<|=======|>>>>>>>)" .gitignore` must print 0, then `add` and `commit --no-edit`. Then `git worktree remove` that worktree and `merge --ff-only` the integration branch into downstream worktrees whose tasks have not started.
- `git worktree remove` failing with "Filename too long" (deep `node_modules` paths on Windows) is handled the same way as the next case: prune, leave the folder and tell the owner the path.
- `git worktree remove` failing with "Permission denied" or "Invalid argument" means a process (dev server, editor, a finished worker's node) still holds files there. Run `git worktree prune`, because the merge is already safe. Leave the folder, note it in ESTADO.md, and tell the owner it can be deleted after the holding process is closed or the machine restarts. Do not force-delete.
- A worker cut by its runtime cap can leave `.git/worktrees/<name>/index.lock`. If no git.exe process is running, delete the lock and retry.
- Preview a merge without touching any worktree using `git merge-tree --write-tree --name-only A B`. In KH, each art feature appends its own `/art-b/<set>/raw/` line to the end of `.gitignore`, so two art branches always conflict there. Keep both lines.
- If a spec task's step 0 is a merge, do that merge yourself before the worker starts and say in a comment that it is already done. Otherwise a conflict stalls a Sonnet run.
- Before pushing a merge, run the full server and client suites on the integrated checkout (`npm test` in server, `npx vitest run` in client, both with `</dev/null`, output to a file, then grep the totals). A merge of two individually green branches can still break, and the pass counts go in the report. In KH, `sharp` is a root-`package.json` devDependency, so the client suite run from a worktree reports `iconSheet.test.js` as "Cannot find module 'sharp'" (a suite failure, not a test failure) and the totals look short. Prefix the vitest run with `NODE_PATH=<integration checkout>/node_modules` (the test header says so) instead of installing `sharp` or skipping the file; confirm the same failure on the base branch before calling it pre-existing. If one other test fails once and then passes on reruns, record it as intermittent-not-reproduced in the review rather than hiding it or blocking on it.
- Before merging, check conflicts with `git merge-tree --write-tree` and read its exit code: 1 means there are conflicts, even though the output looks clean. Two branches can both grab the next free `feature_list.json` id. Keep the id that is already referenced in tasks, branches and the roadmap, renumber the done/fix entry to the next free id, and say so in the merge message.
- Worktrees that symlink `node_modules` to the integration checkout let a worker's `npm install` or `npm ci` damage the main install (for example, `client/node_modules/.bin` disappears and `vitest` is "not recognized"). Fix it with `npm install` in the main checkout, then `git checkout -- package-lock.json`. Do not count that failure as a test failure.
- `git worktree add` creates no `node_modules` at all. Before unblocking a `[GATE]` implementer task, create the two junctions it needs (`client/node_modules` and `server/node_modules`, each pointing at the integration checkout's own `client/node_modules`/`server/node_modules`) — never a single junction at the worktree root. From bash on Windows, `cmd //c mklink ...` silently fails (MSYS rewrites `//c` and cmd just opens an interactive shell with no command run); use `cmd.exe /c "mklink /J <winpath-target> <winpath-source>"` (single slash, whole command quoted, native backslash paths) — that is the form that actually creates the junction. If a stray root-level `node_modules` link exists from an earlier setup, remove only the link (`rm node_modules`), never its destination, and recreate the per-package junctions instead.
- After every merge into the integration branch, refresh the owner's live phone preview: `bash D:/Proyectos/_ops/preview/arrancar.sh` (detached `_preview` worktree, server :3101 + vite :5180, off the workers' 5173/3001). For the setup recipe and the phone-fit checks, see `references/kh-art-pipeline.md` §Persistent live phone preview.
- Mobile and visual evidence ("busca errores visuales", "does it fit a phone", before/after for a layout fix): follow `references/mobile-visual-qa.md`. It covers the Playwright capture set (fast, but blind to 100vh clipping), the real Chrome on an Android emulator, writing findings to disk, grouping them into fix features, and worker before/after captures.
- When several branches are approved in one OK, merge them in one pass, each with `--ff-only` if the base is still its ancestor, otherwise `--no-ff -m "merge: <branch> -> <base> (...)"` (after the first ff, the second branch usually needs `--no-ff`). Then: suites → push → `ls-remote` → preview refresh → remove the merged worktrees → append the result (new HEAD, pass counts, leftover folders) to ESTADO.md. Old [GATE] tasks left in triage after a continuation task finished are history, not pending work; say so instead of reporting them as open. Branches cut from an older base usually all need `--no-ff`; dry-run each against HEAD with `merge-tree` first. Run the suites once, push once.
- When the user asks why there are several checkouts, explain: one repo, one worktree per feature, so agents switching branches never change files under each other; worktrees are removed after merge.

Deviation from the harness, on purpose: the reviewer (not the implementer) marks `done` and writes the CHANGELOG line on APPROVED. It saves one Sonnet run per feature; feature_list.json and CHANGELOG.md are not application code.

Parallel features: each gets its own git worktree (`git worktree add ../<repo>-wt/<name> -b feature/<name>`) and its own task chain; workspace_path points to the worktree. feature_list.json and CHANGELOG.md are the only shared files; edits must be surgical.

## Token budget rules
- Model per task by difficulty, overriding the profile default with kanban_create `model` + its matching `provider`: trivial -> claude-haiku-5-5, normal -> profile default, hard (refactor, security, concurrency, a spec rejected twice) -> claude-opus-5-5 for that task only. If the owner offers or selects an alternate provider, pin both values explicitly; check the executor's provider/quota state before a long dispatch.
- Central's own turns stay short: create tasks, read one-line summaries, report. Do not re-read the spec or the diff unless a task blocks or the user asks.
- When repeated provider 429s block an in-progress task and the owner authorizes another worker/provider, pause or block the original task before dispatching a replacement so only one worker can write the shared worktree. Pin the replacement's model and provider, reuse the same branch/worktree, and carry forward the exact WIP commit, completed checklist items, approved decisions, and remaining acceptance criteria in a comment/body; verify the old task is blocked and the replacement is the only ready writer. If committed work is already present but its Kanban task remains blocked after a provider failure, do not blindly unblock it just to request review: that can respawn the writer. Verify HEAD/status and raw test outputs, keep the human gate closed, and use only a supported safe review transition; if `kanban_request_review` rejects the blocked task, record the limitation and report review as pending instead of claiming a handoff.
- A worker stuck on repeated Vertex 429s (`rate_limited` events, exit 75): put `openai-codex`/`gpt-5.5` FIRST in that profile's `fallback_providers` (config.yaml, keep a `.bak`), keep Vertex after it, and check the board shows a new `spawned` without `rate_limited`. Every fallback entry must name a provider defined in THAT profile's config (`providers:` block) — a provider registered only in central's config is silently unusable by the worker — and local models are excluded by the owner's rule.
- Workers have memory/session_search/browser/delegation disabled; state lives in the repo, not in agent memory.
- One feature per worker run; set `max_runtime_seconds` (spec 1200, implement 3600, review 900, explore 600) so a stuck worker is re-queued instead of burning tokens.
- All profiles share one Anthropic usage window: run at most ~2 Sonnet workers in parallel; Haiku tasks are cheap to parallelize.
- Check the token state with `hermes usage` (session window and weekly window, with reset times) and `hermes insights --days N`. The weekly window is the binding one. At ≥90 % weekly, do not dispatch new Opus turns (p-kh art gates, big reviews). Offer the owner a choice: wait for the reset, or have the owner judge the contact sheet personally. Profiles may have Vertex Gemini fallbacks (recipe in the hermes-agent skill, providers-and-models reference), but a quota-specific 429 is not guaranteed to trigger a fallback; inspect the actual task/provider state before retrying and report pay-per-use implications.
- Gemini image spend (legacy API runs only; KH web generation is free) is not in `run_log.jsonl` (no cost field). Report it as calls × per-image price, labeled as an estimate, and point to the billing account's 30-day spend for the real figure.

fallback es una opción explícita a ofrecer/registrar, no un recorte silencioso.

**Registro para revisión post-reset:** cada vez que una tarea de Kanban se despacha
con `model_override`/`provider_override` distinto del default por este motivo, agregar
una fila a `D:\Proyectos\_ops\FALLBACK_MODEL_LOG.md` (fecha, task id, título, modelo,
motivo). Cuando la quota semanal de Anthropic se resetea (ver `resets in` en
`hermes quota status --cached`), Central lee ese log entero y por cada fila: abre el
resultado real (diff, review.md, brief) y lo evalúa con su propio criterio Claude —
no solo el resumen de una línea del worker. Si algo quedó flojo (spec ambigua, review
superficial, código que un reviewer Haiku/Sonnet habría rechazado), abrir una tarea de
corrección o re-revisar esa pieza; si todo está bien, marcar la fila "revisado: OK" y
reportar un resumen corto al owner (cuántas tareas corrieron en fallback, cuántas
necesitaron corrección).

**No se detiene nada mientras tanto:** el dispatcher de Kanban es un servicio del
gateway, independiente de la sesión de chat de Central — las tareas `ready`/`running`
siguen avanzando aunque la sesión de Central se quede sin tokens o se cierre. Lo único
que se frena es que CENTRAL deje de poder crear tareas nuevas / hacer gates nuevos; el
fallback de arriba es exactamente para que eso no pase.

## Knowledge pack + explorer-first (token policy)
- Each project has `D:\Proyectos\_conocimiento\<proyecto>\PAQUETE.md`, a condensed reference with sources, built once by explorer (pin Sonnet for that one task). Also pin Sonnet on the explorer brief of a big feature (an engine contract to map, an art inventory, a spike to port): Haiku briefs on that scope miss file:line evidence and the spec pays for it. Tell the owner it was Central's call. It lives outside the repo so every branch and worktree shares it with no merge conflicts.
- Before every spec, dispatch an explorer task that writes `briefs/<feature>.md`, and make the spec task depend on it (`parents`). Every task body carries the lines `Conocimiento: <PAQUETE>` and `Brief: <brief>`. The SOULs read them first. On APPROVED, the reviewer appends 1-3 lines to `## Decisiones` and `## Trampas`.
- To change instructions on an existing task there is no body edit: use `kanban_comment` (workers read comments). Use `kanban_link` to add a dependency to a todo task.
- Long-lived Opus agents (central, p-kh) drive >90% of spend through history replay. Keep compression at 0.1, keep state on disk (`D:\Proyectos\_ops\ESTADO.md` for central) and start fresh sessions per topic.

## Working with long-lived project agents (e.g. p-kh)
- Each message_agent to an Opus project agent costs a full turn and lands in its single growing "Bot Chat". Message it only for decisions or art input, never for FYIs. Do cheap mechanical actions yourself, such as an owner-approved push, instead of relaying them.
- Project agents dispatch work via kanban_create (explorer brief → spec → [GATE] impl → reviewer), never delegate_task: those subagents inherit Opus. Art sign-off by the project agent is a Kanban task assigned to it, and the impl task depends on it (kanban_link + block kind=dependency).
- Pipeline work happens in worktrees `D:\Proyectos\<repo>-wt\<feature>`; the project agent's own checkout is off-limits. It marks features it takes with `assignee: "<agent>"` in feature_list.json, so Central skips them.
- Before branching from or merging an agent's branch, run `git show --stat` on its recent commits. A `commit -a` once swept in 9 silently deleted docs. Restore with `git checkout <commit>~1 -- <path>` in its own commit before any merge.
- Generated art needs eyes: the Haiku reviewer cannot judge images and escalates. Central checks the contact sheet and in-scene capture with vision (no transparency, a background or floor strip, several objects in one icon). Send defects to a fix task for the implementer that regenerates, verifies alpha-0 corners with a script, and creates a `[KH][arte] aprobar …` task assigned to the project agent. Link that art task as parent of the review task (`kanban_link`), comment that the reviewer should cite it as visual evidence and review only the new diff, then `kanban_unblock` the review (it goes to todo until the parents finish).
- Art-gate forwarding recipe (worker blocked with `needs_input` on a sheet): convert the `.webp` sheet to PNG with sharp (`NODE_PATH=<main checkout>/node_modules`, node called directly with `</dev/null`) so vision can load it, view the whole sheet and then crops of the new row, run the alpha check on the new sprites, then create `[KH][arte] aprobar P<k> …` for p-kh with: absolute sheet path, which row is new vs. reference, how it was generated (web/other model), what Central already verified, numbered suspicions, and the verdict format `<APROBADO|REGENERAR> -> <resumen>` per sprite. The worker keeps the lot uncommitted until Central comments the verdict; do not touch its uncommitted files meanwhile.
- Before creating an art-gate task, Central views the contact sheet and lists concrete suspicions in the body ("X looks like Y — confirm or discard"), so the art agent answers each instead of a vague pass. Also check the cutouts by measuring alpha inside the sprite, not only by trusting the verifier's ✓ (see kh-art-pipeline.md, Verify). Return technical defects to the implementer before p-kh spends an Opus turn on them.
- Owner asks to try an idea "en forma de prueba" while a feature is mid-flight: run it as a pilot task (`sdd:false`, no spec, criteria in the body) in its own worktree branched from the running feature's latest approved commit, touching only new files plus a dev-only demo, its own Vite port, a small generation cap, and before/after evidence (videos or captures) for the owner. Say it takes one of the 2 Sonnet slots and state the weekly %. Merge it after the feature it branched from. Art-specific recipe (more frames/personality): `references/kh-art-pipeline.md` §Generate.
- When the owner asks to turn a manual workaround Central did by hand into pipeline tooling, write down the working manual recipe first (references/). Then dispatch it as an `sdd:false` implementer task in its own worktree, without a spec, whose body carries the acceptance criteria, an end-to-end test on scratch output, and any owner-only step (a login) as a `needs_input` block. Tell the owner about the risks: the UI changes, and there are terms-of-service and rate-limit concerns.
- At an owner-login gate, verify the session yourself (cookies in the profile, plus a headless probe) before unblocking. A script's own "✓ logged in" can be a false positive.
- On a REGENERAR verdict, pre-create the whole chain at once so it flows without Central: regen fix task (implementer, rejected ids only) → art round-2 task (parents=[regen]) → next stage task (parents=[round 2]). The round-2 body must say "if anything still fails, kanban_block(kind=needs_input), do NOT complete", because completing releases the gated stage onto unapproved art.
- Exception: when the next step after the verdict is another generation lot with its own art gate (a full set after a pilot, or the next T of the same stage, e.g. enemies after heroes), skip the separate round 2. Comment the verdict's prompt rules plus the regen and the full set in one instruction to the implementer, and let p-kh judge the regenerated item on the full contact sheet. This saves one gate round. The risk is more regenerations if the new rules miss, so tell the owner it was Central's call.
- Central gets no wake-up in either direction of an art gate: not when p-kh completes a verdict, and not when the implementer blocks with `needs_input` on a new sheet, so gates sit unrelayed for 10–40 min. When the owner asks to keep agents working persistently, or as soon as a feature has more than one art gate, install the relay cron: `hermes cron create "every 10m" "$(cat <prompt file>)" --name "<project>-relevo" --monitor-script <script> --skill sdd-harness-orchestration --deliver origin --failure-deliver local`. The monitor script (`scripts/kh_watch.sh`, copy it into the profile's `scripts/` dir) prints only actionable board state with no timestamps, so the agent wakes only when the board really changes and costs zero tokens otherwise. The prompt lists the relay rules: relay a finished p-kh verdict to its implementer + unblock (or create a continuation if it fell to triage), create the p-kh gate task when an implementer blocks on a sheet, launch the next stage after a reviewer APPROVED, never merge, cap 2 workers, and answer `[SILENT]` unless the owner must decide. Put `RELAY_TO: <implementer id>` in every p-kh gate body so the relay knows where to forward. Give the owner the pause command (`hermes cron pause <id>`) and log the job id in ESTADO.md. Keep the manual check as a backup: on every owner message while a gated feature is in flight, first run `hermes kanban list | grep -E "running|ready|blocked|triage"` and handle what is waiting before answering, admitting any delay in one line.
- When a set fails verification, split the failures before spending: processing defects (halo, border, padding) are fixed from the raw PNGs at no cost, and only shape failures get regenerated. Never relax the requirement to make the set pass.
- For KH art commands (generate, cut out, icon sheet, alpha check, where each asset is loaded), the web-only generation rule and session check and the recipe to show the running game with screenshots, see `references/kh-art-pipeline.md`; use it in fix-task bodies and owner guides.
- Kanban notifications reach the owner twice: on desktop, because Central auto-subscribes to the tasks it creates, and on Telegram through the reporter.

## Talking to the owner
- Answer "what's next?" in three blocks: already running (no action needed), what the owner will have to approve, and the proposed order as a table with a one-line "why this order" per feature. End with one concrete yes/no question.
- A bare merge OK ("dale ok al merge") covers only the merge offered in the last report. Before merging, list the other unmerged feature branches (`git merge-base --is-ancestor <branch> <base>`) and ask about them by name in the report.
- For a batch of new features that must not break existing work (a roadmap, ideas from reference games), follow `references/additive-roadmap.md`: non-destruction rules R-ND, one card per feature, interleaving with the queue, and its own docs branch.
- When the owner reorders the queue ("pon la N primero"), write the new order in ESTADO.md. Hold the displaced features until N is merged, and base them on the branch that contains N, so they do not inherit the problem N fixes. If N's spec is already done, show its gate questions in the same reply.
- Keep re-asking an open decision in one line at the end of later reports until it is answered; do not launch it without the OK. Never re-ask something already approved. Exception: when a premise of an approved option changes (e.g. a paid option becomes free), ask once whether the choice changes, then record the answer in ESTADO.md ("no re-preguntar") and move on.
- Reviewer non-blocking notes that change what the player sees (e.g. only one enemy shows a health bar) go to the owner as a one-line yes/no at the end of the report. When the owner says yes while another stage of the same feature is running in that worktree, do not dispatch code work in parallel: amend the spec yourself (new numbered R + an inserted `T<n>.5` at the start of the next stage, before the capture/fps task so evidence includes it), commit only the spec files, and comment the running task "spec changed, do NOT do T<n>.5 now". Two writers in one worktree collide, and a change placed after the capture task forces new captures.
- "Should we switch engine?" after visual bugs: first classify each defect by mechanism (layout coordinates, art scale, HUD placement, perf). If they are layout/scale/art, answer no plainly: another engine would reproduce them and cost a rewrite (state the scene's size in lines and its integrations). Emulator fps is not device evidence (GPU is translated); measure on a real phone over USB before blaming the engine, and name texture size as the usual culprit. Say when a switch WOULD pay off (continuous animation/physics/3D, hundreds of moving objects, consoles). Then steer back to the concrete fix (visual sheet, motion integration).
- Owner wording can be loose ("hub" for the combat HUD): pick the reading the context supports, and state the interpretation in the reply instead of asking.
- When an approval message carries a side request (e.g. "apruebo todo, lo único que te pido es una guía de X"), deliver that request in the SAME turn you execute the approval, and write it into `ESTADO.md` as pending until it is done. A side request gets silently dropped across later status reports otherwise, and the owner has to ask again.
- Owner-facing guides (how to test something by hand): write them as a doc in a pipeline worktree (`docs/...`, committed with the feature), never in the project agent's checkout. Put a copy outside the repo where the owner works (e.g. `D:\Proyectos\_arte-pruebas\GUIA.md`) and attach it with `MEDIA:`. Ground every path and command in the real scripts (grep the loaders and the CLI flags) before writing. Summarize the key steps in chat.
- Report results in owner terms (what broke, what was fixed, what is still waiting on them). Decisions taken on their behalf get an explicit "si no te convence, decímelo" line.
- The owner is bothered by error noise. When they ask why there are so many errors, sort them into kinds, from harmless to real:
  1. usage-limit crash notices (`Limit resets at`), which retry on their own;
  2. stale replays and the empty "Your request was not processed" turns those notices produce;
  3. reviewer or art-gate rejections, which are the gate working;
  4. genuine worker mistakes.
  Say which ones needed action, then offer concrete ways to reduce them: smaller tasks, fewer parallel Sonnet runs, and only check whether notices can be grouped.
- Paid external blockers (not KH art, which is web-only): tell the owner the exact place to top up, how many items are left and the estimated cost, and offer the no-cost partial work as an option, not as the default, because it costs an extra round and an extra notice. If they ask to route around the payment (e.g. the web session), check first whether the alternative is really free and gives the same result, and present the options with a recommendation before doing manual work.
- When a new request arrives mid-task (e.g. "open Gemini" while fixing a UI detail), say in the reply where the interrupted task stopped and what is left running for it (a dev server on port N), so it is not lost.

## Pitfalls
- **Persist work while the owner is away:** a worker's request for input is not automatically an owner-only decision. First inspect the task's latest output and resolve reversible technical/operational blockers within the approved scope (for example, allocate an unused test port, use the worktree-local database, or set safe development-only environment variables). Never stop or mutate the owner's main-checkout process/database, borrow its `.env`/secrets, or use a local model when prohibited. Block only when a genuine human decision/credential/approval is required, and keep unrelated safe tasks moving. When a `needs_input` loop sends a task to `triage`, create an idempotent continuation on the same worktree: capture HEAD, staged/unstaged/untracked WIP, tests already run, and remaining acceptance criteria; explicitly forbid reset/discard; pin an authorized cloud provider; verify the successor exists before archiving the old card. Keep the Kanban relay monitor active, pin it to a working authorized cloud provider, and verify the latest run after config changes—an active cron with a provider error is not a persistence mechanism.
- **Autonomous blocker recovery (all implementers/explorers):** a red test, geometry failure, port collision, or suspected spec conflict is not by itself a human gate. Read the complete result, latest owner decision, git status, and concrete failing cases; preserve all thresholds and WIP. First try one evidence-based fix; if it still fails, test a genuinely different strategy (minimal reproducer, measured inputs/bounds, alternate layout/algorithm/environment) and log what changed and why. On the first reversible block, comment the next approach and resume the same card only if it is the sole writer. On a second block/triage, create a continuation on the same worktree with the failed approaches and evidence, and require a distinct next strategy—not a replay. Cap recovery at two distinct alternatives per cause; if both fail, stop and ask only the smallest real unresolved decision, backed by measurements. Never relax tests/specs, bypass approval/security gates, overwrite WIP, spawn parallel writers, or make destructive/paid/auth actions without authorization. Carry this policy in the Kanban relay prompt so recovery happens when Central is away.
When an owner-approved feature is stalled by stale `feature_list.json` metadata, read `docs/specs.md`, the feature's `review.md`, and the owner approval record first. If the work remains authorized and no conflicting task/agent owns the worktree, coordinate with the prior non-null assignee, then restore `status: in_progress` and set `assignee` to the active implementer; do not ask the owner to repeat the approval. Preserve other WIP and record the correction in the Kanban handoff.
- The review dispatcher force-loads skill `sdlc-review` on reviewer runs; a profile created with `--no-skills` crashes ("Unknown skill(s): sdlc-review") until the skill is copied into its `skills/devops/`. Any new reviewer profile needs it.
- Workers commit with the repo's local git identity; there is no global `user.name`. Set `git config user.name/email` in new repos before dispatching.
- Hermes cron runs scripts without a stdin handle: Python `subprocess.run` must pass `stdin=subprocess.DEVNULL` (WinError 6 otherwise). Cron `deliver` must name a platform configured in the cron's own profile (central has no Telegram), so scripts send by themselves and use deliver=local.
- All Anthropic models here have a 1M window and the default `compression.threshold` 0.5 lets contexts reach ~500k tokens per call. Workers, p-kh and central all run at 0.1.
- New profiles from `hermes profile create` start on the root default model (llamacpp) or a copied one; always set `model.default` explicitly. Anthropic credentials come from the shared root credential pool, so no keys are needed per profile.
- `write_file` refuses to overwrite a profile's SOUL.md (default or cloned) unless it was read in full in the session, and a `read_file` with `limit` does not count. If it still refuses, `mv SOUL.md SOUL.md.<origin>-orig` and write the new file (keeps the original as backup).
- A notification saying "worker crashed" or "gave up after repeated spawn failures" means the shared Anthropic usage window ran out when the worker's last output contains `Limit resets at HH:MM`. It is not a Hermes spawn bug. The dispatcher retries after the reset, so do not relaunch or debug; tell the owner in one line and wait for the stage result.
- These crash notices are often replayed after the task is already done (same pid, old reset time). Check `hermes kanban list | grep <id>` first; if done, tell the owner in one line it is a stale repeat.
- Owner decisions that arrive while a spec task is already running: `kanban_comment` them on the spec task as RESOLVED (not open questions), note in ESTADO.md "verify on delivery", and on spec_ready grep requirements/design for them; return the spec if missing.
- If the terminal tool shows only "exit ?, 1 lines output", redirect to a file under `/tmp` and `cat` it in a second terminal call (`read_file` resolves /tmp differently from git-bash, so it reports not found).
- A task in review or ready that never gets dispatched (`respawn_guarded blocker_auth` events, or the gateway logs "kanban dispatcher stuck") is usually held by a stale `last_failure_error` left over from a rate-limit. Look for those events after any usage-limit episode. For the fix and the triage-loop workaround, see `references/kanban-stuck-tasks.md`.
- Verify board actions a worker claims (e.g. "I created the art task") with `hermes kanban list | grep <title>` before reporting them or gating on them.
- After any context compaction or long gap, re-verify live state (`kanban_show` on the tasks in play, `git log --oneline` on the integration branch and the worktree) before continuing a carried-over multi-step plan. The dispatcher and other workers keep moving tasks (review, merge, push) while you were gone; a stale summary can describe a step as "still pending" that is already done several commits later, and redoing it wastes a turn or re-triggers a worker on a task that is no longer theirs to run. After dispatch, verify the task's latest status and newest run/event before telling the owner an agent is working: a run can start and immediately finish blocked, so a transient `running` result is not enough. Report whether the current task is running, queued, or blocked and the actual blocker; explain that sequential reviewers/visual reviewers are waiting on their gate rather than "working" concurrently.
- A worker reply that is not a one-line `<state> -> <path>` means it ignored the protocol: read the file it points to, not its chat text.
- `hermes kanban show <id>` truncates the run summary to one line, which cuts a p-kh verdict mid-sentence. Read the full text from `hermes kanban show <id> --json` piped to Python, walking the JSON for the longest string that starts with the verdict header (the task body also matches "REGENERAR", so do not match on that word alone). Relay the full verdict, never the truncated line.
